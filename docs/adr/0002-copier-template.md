# Copier for generating and updating projects

Projects used to be generated by `create-python-project.sh`, which cloned this
repo, renamed `zamazingo` with sed, patched files per project type and deleted
itself. That made generation a one-way copy: every later improvement to the
template (rails, CI jobs, the sandbox loop) had to be hand-ported into each
service, and the four services generated so far had already drifted from the
template and from each other. The rails checker could detect drift in the rules
but could not deliver fixes.

We moved the template into `template/` and render it with Copier. A generated
project records its answers in `.copier-answers.yml`, and `copier update`
merges template changes into it three-way, so local edits survive.

## Considered Options

- **Keep the sed generator, add a sync script that overwrites managed files**:
  simpler, but an overwrite loses local edits and gives no merge.
- **Monorepo for the services**: rejected separately; the services share
  tooling, not code, and deploy independently.
- **Copier (chosen)**: purpose-built for template updates with three-way merge.

## Consequences

- The repo root is no longer a runnable skeleton. The skeleton is proven by the
  test suite, which renders every project type and runs the rails checker on
  it, and by a CI matrix that builds each rendered type with its own flake.
- Files are split into template-managed and project-owned (`_skip_if_exists`).
  Project-owned files (`pyproject.toml`, `CLAUDE.md`, the package, ...) are not
  updated; the rails checker still enforces their invariants.
- GitHub Actions `${{ }}` expressions collide with Jinja, so a templated
  workflow wraps everything except its templated lines (the default branch) in
  `{% raw %}`. Type-dependent workflows are selected by templated filenames.
- The template converged on what the services had independently arrived at:
  setuptools-scm versions, multi-arch (amd64 + arm64) images with SBOM and
  provenance, and a configurable default branch.
